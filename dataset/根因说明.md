## bug_001: ALU 加减/比较结果错误

```text
group: alu
family: alu_add_sub_result_wrong
bug_id: bug_001
patch: /home/meow/iccad/bug_patches/bug_001.patch
```

修改位置：

```text
rtl/ibex_alu.sv
ALU adder operand B negate control
大致位置: adder_op_b_negate case block，约第 60-72 行
```

原始逻辑：

```systemverilog
      // MinMax OPs (RV32B Ops)
      ALU_MIN,  ALU_MINU,
      ALU_MAX,  ALU_MAXU: adder_op_b_negate = 1'b1;
```

注入后：

```systemverilog
      // MinMax OPs (RV32B Ops)
      ALU_MIN,  ALU_MINU,
      ALU_MAX,  ALU_MAXU: adder_op_b_negate = 1'b0;
```

实际影响：

这个 case item 前面还包括 `ALU_SUB`、`ALU_EQ`、`ALU_NE`、`ALU_GE`、`ALU_LT`、`ALU_SLT` 等操作。因此这不是只影响 `ALU_MAX/ALU_MAXU`，而是会让一组依赖 `operand_a - operand_b` 的 ALU 操作错误地使用非取反的 `operand_b`。

可能影响包括：

- `sub`、`c.sub` 等减法结果错误。
- 比较类指令结果错误，例如 `slt/sltiu` 一类操作。
- 分支条件依赖比较结果时，可能进一步导致控制流错误。
- cosim scoreboard 通常会报告寄存器写回值 mismatch。

已观察到的日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
```

典型例子：

```text
Register write data mismatch to x11 DUT: 37c8e07f expected: 37d8e035
Register write data mismatch to x18 DUT: 0 expected: 1
```

## bug_002: ALU 比较 signedness 错误

```text
group: alu
family: alu_compare_signedness_wrong
bug_id: bug_002
patch: /home/meow/iccad/bug_patches/bug_002.patch
```

修改位置：

```text
rtl/ibex_alu.sv
Comparison signedness selection
大致位置: cmp_signed always_comb，约第 119-130 行
```

原始逻辑：

```systemverilog
      ALU_GE,
      ALU_LT,
      ALU_SLT,
      // RV32B only
      ALU_MIN,
      ALU_MAX: cmp_signed = 1'b1;
```

注入后：

```systemverilog
      ALU_GE,
      ALU_LT,
      ALU_SLTU,
      // RV32B only
      ALU_MIN,
      ALU_MAX: cmp_signed = 1'b1;
```

实际影响：

`ALU_SLT` 本应按 signed comparison 处理，被移出了 signed 列表后会走默认 unsigned 路径。`ALU_SLTU` 本应按 unsigned comparison 处理，被加入 signed 列表后会被错误当成 signed comparison。

可能影响包括：

- `slt` / `slti` 对负数和正数比较时结果错误。
- `sltu` / `sltiu` 在最高位不同时结果错误。
- 后续寄存器写回值与 Spike 不一致。
- 如果比较结果参与条件分支或地址计算，可能间接引发 PC mismatch。

预期日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
```

这个 bug 和 `bug_001` 同属 ALU，但根因更细，主要集中在 signed/unsigned compare 混淆。

## bug_003: 算术右移退化为逻辑右移

```text
group: alu
family: alu_shift_arithmetic_wrong
bug_id: bug_003
patch: /home/meow/iccad/bug_patches/bug_003.patch
```

修改位置：

```text
rtl/ibex_alu.sv
Shift arithmetic control
大致位置: shift_arith assignment，约第 322 行
```

原始逻辑：

```systemverilog
assign shift_arith  = (operator_i == ALU_SRA);
```

注入后：

```systemverilog
assign shift_arith  = 1'b0;
```

实际影响：

`SRA` / `SRAI` 需要算术右移，即右移时用符号位填充高位。注入后 `shift_arith` 永远为 0，算术右移会表现得更像逻辑右移。对最高位为 1 的负数操作数影响最明显。

可能影响包括：

- `sra` / `srai` 结果错误。
- 由错误移位结果参与后续比较、地址计算、分支判断时，会进一步造成更晚的 mismatch。
- 同一个 bug 可能表现为 register mismatch，也可能表现为 PC mismatch。

已观察到的日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
UVM_FATAL Cosim mismatch PC mismatch
```

典型例子：

```text
PC mismatch, DUT retired : 80003620 , but the ISS retired: 80003604
Register write data mismatch to x13 DUT: f expected: ffffffff
```

这个现象很有价值：同一个 injected bug 会产生不同可观测失败症状，适合测试聚类算法是否能识别同源根因。

## bug_005: BEQ/BNE 分支条件互换

```text
group: branch
family: branch_condition_wrong
bug_id: bug_005
patch: /home/meow/iccad/bug_patches/bug_005.patch
```

修改位置：

```text
rtl/ibex_decoder.sv
OPCODE_BRANCH decode
大致位置: branch ALU operator decode，约第 742-746 行
```

原始逻辑：

```systemverilog
          3'b000:  alu_operator_o = ALU_EQ;
          3'b001:  alu_operator_o = ALU_NE;
```

注入后：

```systemverilog
          3'b000:  alu_operator_o = ALU_NE;
          3'b001:  alu_operator_o = ALU_EQ;
```

实际影响：

`instr[14:12] == 3'b000` 对应 `BEQ`，`3'b001` 对应 `BNE`。注入后：

```text
BEQ 被当作 BNE 判断
BNE 被当作 BEQ 判断
```

可能影响包括：

- 条件分支 taken/not-taken 决策反转。
- RTL 和 ISS 很快走向不同 PC。
- trace 中 PC 流会出现明显分叉。
- regr/sim 日志更可能出现 PC mismatch，而不是单纯寄存器写回 mismatch。

预期日志表象：

```text
UVM_FATAL Cosim mismatch PC mismatch
```

也可能先表现为后续错误路径上的寄存器写回 mismatch。

这个 bug 是当前数据集中的第一个控制流类 bucket，和 ALU/LSU 数据通路类 bug 的日志模式有较好区分度。

## bug_008: Load 符号扩展方向错误

```text
group: loadstore
family: load_sign_extend_wrong
bug_id: bug_008
patch: /home/meow/iccad/bug_patches/bug_008.patch
```

修改位置：

```text
rtl/ibex_decoder.sv
Load instruction sign extension decode
大致位置: OPCODE_LOAD decode，约第 323 行
```

原始逻辑：

```systemverilog
        data_sign_extension_o = ~instr[14];
```

注入后：

```systemverilog
        data_sign_extension_o = instr[14];
```

实际影响：

RISC-V load 指令中，`LB/LH` 需要 sign extension，`LBU/LHU` 需要 zero extension。原逻辑用 `~instr[14]` 区分 signed 和 unsigned load。注入后逻辑被反转：

```text
LB/LH 可能被错误零扩展
LBU/LHU 可能被错误符号扩展
```

可能影响包括：

- 从内存读出最高位为 1 的 byte/halfword 时，写回寄存器值错误。
- `load` 后续参与 ALU、branch 或 store 时，错误会传播。
- cosim scoreboard 通常报告 register write mismatch。

预期日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
```

这个 bug 属于 LSU/load 数据后处理路径，和 `bug_009` 的 store byte enable 错误属于同一粗粒度 group，但 failure mechanism 不同。

## bug_009: Store byte enable 错误

```text
group: loadstore
family: store_byte_enable_wrong
bug_id: bug_009
patch: /home/meow/iccad/bug_patches/bug_009.patch
```

修改位置：

```text
rtl/ibex_load_store_unit.sv
Byte-enable generation for byte stores
大致位置: BE generation，约第 154-160 行
```

原始逻辑：

```systemverilog
      2'b10,
      2'b11: begin // Writing a byte
        unique case (data_offset)
          2'b00:   data_be = 4'b0001;
          2'b01:   data_be = 4'b0010;
          2'b10:   data_be = 4'b0100;
          2'b11:   data_be = 4'b1000;
```

注入后：

```systemverilog
      2'b10,
      2'b11: begin // Writing a byte
        unique case (data_offset)
          2'b00:   data_be = 4'b0001;
          2'b01:   data_be = 4'b0100;
          2'b10:   data_be = 4'b0100;
          2'b11:   data_be = 4'b1000;
```

实际影响：

当执行 byte store 且地址低两位 `data_offset == 2'b01` 时，原本应写 byte lane 1，即 `data_be = 4'b0010`。注入后错误写成 `4'b0100`，会写到 byte lane 2。

可能影响包括：

- `SB` 写入错误字节位置。
- 同一个 word 内目标 byte 未更新，旁边 byte 被错误覆盖。
- 后续 load 读回内存时与 ISS 不一致。
- 如果被错误写坏的是控制数据或签名区域，可能进一步造成更多间接 mismatch。

预期日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
```

也可能在后续内存比较或签名检查阶段暴露。

## bug_010: CSR set/clear 操作语义互换

```text
group: csr
family: csr_op_set_clear_swap
bug_id: bug_010
patch: /home/meow/iccad/bug_patches/bug_010.patch
```

修改位置：

```text
rtl/ibex_cs_registers.sv
CSR operation logic
大致位置: csr_op_i always_comb，约第 825-833 行
```

原始逻辑：

```systemverilog
      CSR_OP_WRITE: csr_wdata_int =  csr_wdata_i;
      CSR_OP_SET:   csr_wdata_int =  csr_wdata_i | csr_rdata_o;
      CSR_OP_CLEAR: csr_wdata_int = ~csr_wdata_i & csr_rdata_o;
      CSR_OP_READ:  csr_wdata_int = csr_wdata_i;
```

注入后：

```systemverilog
      CSR_OP_WRITE: csr_wdata_int =  csr_wdata_i;
      CSR_OP_SET:   csr_wdata_int = ~csr_wdata_i & csr_rdata_o;
      CSR_OP_CLEAR: csr_wdata_int =  csr_wdata_i | csr_rdata_o;
      CSR_OP_READ:  csr_wdata_int = csr_wdata_i;
```

实际影响：

`CSR_OP_SET` 本应把写入 mask 中为 1 的 bit 置位，`CSR_OP_CLEAR` 本应把写入 mask 中为 1 的 bit 清零。注入后两者语义互换，CSRRS/CSRRC 以及对应 immediate 形式会写出错误的 CSR 值。

可能影响包括：

- `csrrs/csrrsi` 对 CSR bit 的置位效果变成清零效果。
- `csrrc/csrrci` 对 CSR bit 的清零效果变成置位效果。
- `mstatus`、`mie`、`mtvec`、performance counter control 等 CSR 被错误更新后，后续中断使能、trap 返回、计数器行为可能偏离 ISS。
- 如果 CSR 读回值参与普通寄存器写回，通常会先表现为 register write data mismatch。
- 如果错误 CSR 状态影响异常、中断或控制流，后续也可能表现为 PC mismatch 或 trap 行为不一致。

预期日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
UVM_FATAL Cosim mismatch PC mismatch
```

这个 bug 是当前数据集中的 CSR 类 bucket，用来补足此前 ALU、branch、loadstore 之外的系统寄存器状态类根因。

## bug_011: 非法指令 trap 被屏蔽

```text
group: exception
family: illegal_instr_trap_missing
bug_id: bug_011
patch: /home/meow/iccad/bug_patches/bug_011.patch
```

修改位置：

```text
rtl/ibex_controller.sv
Illegal instruction exception request generation
大致位置: illegal_insn_d assignment，约第 200-205 行
```

原始逻辑：

```systemverilog
assign illegal_insn_d = illegal_insn_i & (ctrl_fsm_cs != FLUSH);
```

注入后：

```systemverilog
assign illegal_insn_d = 1'b0;
```

实际影响：

`illegal_insn_i` 是 decoder、CSR 权限检查、RV32E 非法寄存器访问、非法压缩指令等路径汇总出来的非法指令信号。原本 controller 会在合适状态下把它记录为 `illegal_insn_d`，进而触发 illegal instruction exception。注入后该信号被强制清零，非法指令不会按预期进入 trap 流程。

可能影响包括：

- 非法指令本应 trap，但 DUT 继续执行或进入错误状态。
- `mcause/mepc/mtval` 等异常相关 CSR 不会按 ISS 预期更新。
- 原本应跳转到 trap vector 的 PC 没有跳转，容易产生 PC mismatch。
- 如果非法 CSR 或非法系统指令被错误忽略，后续可能表现为 CSR read/write mismatch 或寄存器写回 mismatch。

预期日志表象：

```text
UVM_FATAL Cosim mismatch PC mismatch
UVM_FATAL Cosim mismatch Register write data mismatch
```

这个 bug 是当前数据集中的 exception/trap 类 bucket，和 `bug_005` 的 branch 控制流错误不同：`bug_005` 是普通条件分支判断反了，`bug_011` 是异常控制流入口被屏蔽。

## bug_012: Pipeline forwarding 数据旁路失效

```text
group: pipeline
family: forwarding_data_wrong
bug_id: bug_012
patch: /home/meow/iccad/bug_patches/bug_012.patch
```

修改位置：

```text
rtl/ibex_id_stage.sv
Register file writeback forwarding path
大致位置: rf_rdata_b_fwd assignment，约第 990-995 行
```

原始逻辑：

```systemverilog
assign rf_rdata_b_fwd = rf_rd_b_wb_match & rf_write_wb_i ? rf_wdata_fwd_wb_i : rf_rdata_b_i;
```

注入后：

```systemverilog
assign rf_rdata_b_fwd = rf_rdata_b_i;
```

实际影响：

Ibex 在 ID 阶段会对寄存器读数据做 writeback forwarding：当前指令读取的源寄存器如果正好等于 WB 阶段正在写回的目标寄存器，就直接使用最新写回值，避免读到旧的 register file 内容。注入后，B 操作数的 forwarding 被关闭，`rs2` 相关的数据相关冒险会读到旧值。

可能影响包括：

- 相邻或近距离相关指令中，第二条指令的 `rs2` 使用旧值。
- 影响二操作数 ALU 指令，例如 `add/sub/and/or/xor/sll/srl/sra`。
- 影响 store 数据通路，因为 store 写入数据通常来自 `rs2`。
- 影响 branch 比较操作数，可能进一步造成 taken/not-taken 判断错误和 PC mismatch。
- failure 位置可能不在真正的 forwarding 发生点，而是在后续寄存器写回、store/load 回读或分支路径分叉时暴露。

预期日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
UVM_FATAL Cosim mismatch PC mismatch
```

这个 bug 是当前数据集中的第一个 pipeline 类 bucket。它和 `bug_001/002/003` 的 ALU 计算逻辑错误不同：ALU 本身可以是对的，但输入操作数因为流水线旁路失效而变旧。

## bug_013: JALR target base 选择错误

```text
group: jump
family: jalr_target_base_wrong
bug_id: bug_013
patch: /home/meow/iccad/bug_patches/bug_013.patch
```

修改位置：

```text
rtl/ibex_decoder.sv
JALR target operand mux selection
大致位置: OPCODE_JALR decode，约第 720-732 行
```

原始逻辑：

```systemverilog
      OPCODE_JALR: begin // Jump and Link Register
        if (BranchTargetALU) begin
          bt_a_mux_sel_o = OP_A_REG_A;
          bt_b_mux_sel_o = IMM_B_I;
        end

        // Jumps take two cycles without the BTALU
        if (instr_first_cycle_i && !BranchTargetALU) begin
          // Calculate jump target
          alu_op_a_mux_sel_o  = OP_A_REG_A;
          alu_op_b_mux_sel_o  = OP_B_IMM;
          imm_b_mux_sel_o     = IMM_B_I;
          alu_operator_o      = ALU_ADD;
```

注入后：

```systemverilog
      OPCODE_JALR: begin // Jump and Link Register
        if (BranchTargetALU) begin
          bt_a_mux_sel_o = OP_A_CURRPC;
          bt_b_mux_sel_o = IMM_B_I;
        end

        // Jumps take two cycles without the BTALU
        if (instr_first_cycle_i && !BranchTargetALU) begin
          // Calculate jump target
          alu_op_a_mux_sel_o  = OP_A_CURRPC;
          alu_op_b_mux_sel_o  = OP_B_IMM;
          imm_b_mux_sel_o     = IMM_B_I;
          alu_operator_o      = ALU_ADD;
```

实际影响：

RISC-V `JALR` 的跳转目标应由 `rs1 + imm` 计算得到，并用于间接跳转或函数返回。注入后，target base 从 `rs1` 错误改成当前 PC，导致 `JALR` 退化成近似 PC-relative jump。对于函数调用返回、寄存器间接跳转、压缩 `C.JR/C.JALR` 展开后的路径，DUT 很容易走向和 ISS 不同的 PC。

可能影响包括：

- `jalr` 跳转到错误地址。
- `ret` / `jr` / `c.jr` / `c.jalr` 等间接跳转行为错误。
- DUT 和 ISS 的 retired PC 很快分叉，通常表现为 PC mismatch。
- 如果错误路径上继续执行一段时间，也可能先出现寄存器写回 mismatch 或 illegal instruction trap。

预期日志表象：

```text
UVM_FATAL Cosim mismatch PC mismatch
UVM_FATAL Cosim mismatch Register write data mismatch
```

这个 bug 和 `bug_005` 都属于控制流相关失败，但根因不同：`bug_005` 是条件分支的 taken/not-taken 判断错误，`bug_013` 是间接跳转 target base 选择错误。

## bug_014: OP-IMM 操作数 B mux 选择错误

```text
group: decode
family: opimm_operand_b_mux_wrong
bug_id: bug_014
patch: /home/meow/iccad/bug_patches/bug_014.patch
```

修改位置：

```text
rtl/ibex_decoder.sv
Register-immediate ALU operand mux selection
大致位置: OPCODE_OP_IMM decode，约第 820-823 行
```

原始逻辑：

```systemverilog
      OPCODE_OP_IMM: begin // Register-Immediate ALU Operations
        alu_op_a_mux_sel_o  = OP_A_REG_A;
        alu_op_b_mux_sel_o  = OP_B_IMM;
        imm_b_mux_sel_o     = IMM_B_I;
```

注入后：

```systemverilog
      OPCODE_OP_IMM: begin // Register-Immediate ALU Operations
        alu_op_a_mux_sel_o  = OP_A_REG_A;
        alu_op_b_mux_sel_o  = OP_B_REG_B;
        imm_b_mux_sel_o     = IMM_B_I;
```

实际影响：

`OPCODE_OP_IMM` 覆盖 RISC-V register-immediate ALU 指令，例如 `addi/slti/sltiu/xori/ori/andi/slli/srli/srai`。这些指令的 B 操作数本应来自 I-type immediate。注入后，B 操作数错误地来自寄存器 B 读口，导致 immediate 指令按近似 register-register 形式执行。

可能影响包括：

- `addi` 等立即数算术结果错误。
- `andi/ori/xori` 等立即数逻辑结果错误。
- `slti/sltiu` 比较对象错误。
- shift-immediate 指令的 shift amount 可能来自错误数据路径，造成移位结果不一致。
- 由于 OP-IMM 指令在随机测试中很常见，该 bug 通常会快速暴露为寄存器写回 mismatch。

预期日志表象：

```text
UVM_FATAL Cosim mismatch Register write data mismatch
UVM_FATAL Cosim mismatch PC mismatch
```

这个 bug 是当前数据集中的第一个 decode 类 bucket。它和 `bug_001/002/003` 的 ALU 内部计算错误不同：ALU 计算单元本身可以正常，但 decoder 选择了错误的操作数来源。

- 粗粒度区分：`alu`、`branch`、`jump`、`loadstore`、`csr`、`system`、`exception`、`pipeline`、`decode`、`multdiv`、`interrupt`、`fetch` 的日志模式和 trace 表现不同。
